# Test Result

## Functionality
- [ ] FT-01: Resident can sign up for an account with valid details.
  - Action: Open the Sign Up form, enter a name, a valid email, and a password, click "Sign Up".
  - Expected: Account is created and the user is signed in and taken to the alerts feed.
  - Bug Report:
    - Issue: Missing Feature — No Sign Up / Account Creation Flow
    - Actual: No Sign Up form exists anywhere in the application. The header contains only "New Post", a notification button ("3"), and a fixed user chip ("Sarah"); there are no sign-up/sign-in links or buttons in the DOM, and the routes /signup, /sign-up, /register, /login, and /auth all render the app's 404 page. The site is permanently pre-authenticated as "Sarah Mitchell", so an account cannot be created and the sign-in/redirect flow cannot occur.
- [X] FT-02: Signed-in user can create a short post.
  - Action: Click "Create Post", enter a title and body text, select a category, click "Post".
  - Expected: The new post appears at the top of the alerts feed with its title and body.
- [X] FT-03: User can categorize a post as "Safety Alert".
  - Action: Create a post with category "Safety Alert" selected.
  - Expected: The saved post displays the label "Safety Alert".
- [ ] FT-04: User can categorize a post as "Lost and Found".
  - Action: Create a post with category "Lost and Found" selected.
  - Expected: The saved post displays the label "Lost and Found".
  - Bug Report:
    - Issue: Incorrect Category Label Text
    - Actual: The saved post displays the label "Lost & Found" (same wording is used in the category picker and the filter bar) instead of the expected label "Lost and Found".
- [X] FT-05: User can categorize a post as "Community Event".
  - Action: Create a post with category "Community Event" selected.
  - Expected: The saved post displays the label "Community Event".
- [X] FT-06: Feed shows recent alerts in reverse-chronological order.
  - Action: Open the main feed page and observe the order of the default posts.
  - Expected: All default posts are listed, newest first, with visible timestamps.
- [X] FT-07: User can filter the feed by category.
  - Action: Select "Safety Alert" in the category filter control.
  - Expected: The feed shows only posts labeled "Safety Alert"; posts of other categories are hidden.
- [X] FT-08: User can search the feed by keyword.
  - Action: Type a word present in one default post's title or body into the search field and submit.
  - Expected: The feed shows only posts containing that keyword.
- [X] FT-09: User can comment on a post.
  - Action: Open a default post, type text into its comment field, click "Comment".
  - Expected: The comment appears under that post with its text and author.
- [X] FT-10: User can mark an alert as resolved.
  - Action: Click "Mark as Resolved" on a post.
  - Expected: The post is updated to show a "Resolved" status.
- [ ] FT-11: User can mark an alert as no longer relevant.
  - Action: Click "Mark as No Longer Relevant" on a post.
  - Expected: The post is updated to show a "No Longer Relevant" status.
  - Bug Report:
    - Issue: Missing Feature — No "Mark as No Longer Relevant" Control
    - Actual: Post cards expose only "Mark Resolved" (or "Reopen" when already resolved) as status actions; no button, menu item, or other control containing "No Longer Relevant" exists anywhere in the page (zero DOM/text matches for "relevant"), so a post can never be marked "No Longer Relevant" and no such status is ever displayed.

## Constraint
- [ ] CS-01: Sign up form cannot be submitted with empty required fields.
  - Action: Leave name, email, or password empty and click "Sign Up".
  - Expected: Submission is blocked and a message indicates the missing field(s); no account is created.
  - Bug Report:
    - Issue: Unverifiable — Missing Sign Up Form (Constraint Cannot Be Executed)
    - Actual: There is no Sign Up form to leave fields empty in: the application has no authentication UI at all and /signup, /sign-up, /register, /login, /auth all return the 404 page, so the empty-required-fields scenario cannot be executed and the expected validation message cannot be produced or verified.
- [ ] CS-02: Sign up is rejected for an already-registered email.
  - Action: Sign up using the email of an existing user.
  - Expected: Submission is rejected with a message that the email is already registered; no duplicate account is created.
  - Bug Report:
    - Issue: Unverifiable — Missing Sign Up Form (Constraint Cannot Be Executed)
    - Actual: Duplicate-email rejection cannot be exercised because the app provides no sign-up form or auth flow (no auth controls in the DOM; /signup, /register, /login routes render 404), so no "email already registered" message can ever be triggered.
- [ ] CS-03: A post cannot be created with an empty title or body.
  - Action: Click "Create Post", leave the title or body empty, click "Post".
  - Expected: Submission is blocked with a validation message; no post is added to the feed.
  - Bug Report:
    - Issue: Missing Validation Message on Incomplete Post Submission
    - Actual: With the body filled and title empty (and vice versa) the "Post to Neighborhood" button stays disabled and clicking it gives no feedback whatsoever — no validation message identifies the missing field. Submission is blocked only via the silently disabled button; while no post was added to the feed, the expected validation message never appears.
- [ ] CS-04: A post cannot be created without a category.
  - Action: Click "Create Post", enter title and body, leave the category unselected, click "Post".
  - Expected: Submission is blocked with a message that a category is required.
  - Bug Report:
    - Issue: Missing Category Validation — Category Is Pre-Selected and Post Submits Without Explicit Choice
    - Actual: The Create New Post dialog opens with "Community Event" already highlighted/pre-selected (its button carries the selected styling while "Safety Alert" and "Lost & Found" do not). With title and body filled and no category clicked, the "Post to Neighborhood" button is enabled and clicking it immediately created the post (saved with label "Community Event"). Submission was not blocked and no "category is required" message was shown.
